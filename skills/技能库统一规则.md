# 技能库统一规则

> **本文档需要你先填一行。** 把下面的 `<技能库路径>` 换成脚本打印给你的实际路径，
> 不填的话 AI 会拿字面量当目录去扫，什么也找不到。
>
> ```
> 唯一技能库位置：<在这里填上你的技能库路径>
> ```
>
> 安装脚本会自动选位置（挑空间够的非系统盘建 `AI-Skills`，或退回用户目录），
> 装完会打印一行真实路径，把它抄到上面就行。

---

## 一、铁律

1. **动手之前先查技能库。** 任何任务开始前，先扫一遍技能库有没有现成技能。
2. **有就用，不要现场造轮子。** 已有技能覆盖的场景，禁止临时写脚本替代。
3. **没有就写进技能库。** 做完一段可复用的工作流，沉淀成 `SKILL.md` 放进去，
   不要只留在对话里 —— 下次还得重写一遍。
4. **新技能必须合规**：`SKILL.md` 开头是 YAML frontmatter，含 `name:` 和 `description:`。
   `description` 要写清**触发语**（用户怎么说会命中它）——
   这是 AI 判断要不要读这个技能的唯一依据，不写触发语就等于没发布。

---

## 二、技能目录必须是扁平的

```
<技能库>/<技能名>/SKILL.md                        ✅ 各家都扫得到
<技能库>/分类/演示/某技能/SKILL.md        ❌ 只扫一层，读不到
```

**不要在技能库根目录下建分类子目录。** 分类信息写在 `description` 里，
让 AI 用文字匹配，而不是用目录结构。

---

## 三、各 AI 的技能目录映射

统一库只有一份真实来源，各家通过**符号链接**指过去。库更新一次，全家同步，
不会出现「Cursor 有 63 个、Claude Code 只有 63 个」的版本分叉。

| AI | 技能目录 | 指向 |
| --- | --- | --- |
| WorkBuddy | `%USERPROFILE%\.workbuddy\skills` | → 技能库 |
| Cursor | `%USERPROFILE%\.cursor\skills` | → 技能库 |
| Claude Code | `%USERPROFILE%\.claude\skills` | → 技能库 |
| VS Code | 用 `AGENTS.md` / settings，不扫 skills | — |
| Cursor BYOK | 用 `rules/` 目录 | — |

检查链接是否正常：

```powershell
Get-Item "$env:USERPROFILE\.workbuddy\skills" -Force | Select-Object Name, LinkType, Target
```

## 四、工具在哪

**不要假设工具在 PATH 里。** 很多 AI 工具跑在受限沙箱里拿不到完整环境变量，
靠 PATH 找 `git` / `gcc` 会直接失败。调用一律写绝对路径。

| 工具 | 路径怎么来的 |
| --- | --- |
| git | 装工具时定的目录，见 `<工具目录>` |
| gh（GitHub CLI） | 同上 |
| gcc / g++ | 同上（MinGW-w64） |
| node / python | 如果装过 WorkBuddy，用它自带的托管版本，路径形如 `%USERPROFILE%\.workbuddy\binaries\<name>\versions\<ver>\<exe>` |
| Edge 无头 | `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe` |

**把这段填成你的实际路径**，之后所有调用就不用每次现推：

| 工具 | 完整路径 |
| --- | --- |
| git | （填你的） |
| gh | （填你的） |
| gcc | （填你的） |

> ⚠️ **PATH 里不要同时有两份 MinGW**（Git 自带一份、独立的 mingw64 一份）。
> 那样 `gcc` 会随机命中不同版本，表现为「昨天能编，今天同一个命令报错」。

## 六、GitHub 军火库流程

拿 GitHub 上的代码时，**先查 License 再用**：

1. `gh search repos` / `gh search code` 搜
2. `gh repo view <owner>/<repo> --json licenseInfo,pushedAt` 看许可和维护状态
3. `gh issue list -R <owner>/<repo>` 读别人踩过的坑
4. `gh repo clone <owner>/<repo>` 克隆

| License | 能不能用 |
| --- | --- |
| MIT / Apache-2.0 / BSD | 可以，**但必须保留原始版权声明** |
| GPL-3.0 | 用了就**必须把你的项目也开源** |
| AGPL-3.0 | 连 SaaS / 网络服务都算分发，同样要开源 |
| 无 License | 默认版权保留，**没有授权，不能用** |

要开源的项目别引入 GPL 依赖。`pushedAt` 超过半年没动过的仓库基本是坑。

抄完必须在文件头注明来源 —— 见 `git-github/Git与GitHub使用教程.md`。

## 七、隐私红线（所有对外产物都要过）

交付前必须扫一遍，命中就得改：

- 昵称、真实姓名、手机号、邮箱、本机绝对路径 —— 一个都不能出现
- 正则：`1[3-9]\d{9}` 找手机号，`[\w.+-]+@[\w-]+\.[\w.]+` 找邮箱
- ⚠️ `glob` 默认**不下钻 `.` 开头的目录**（如 `.workbuddy`、`.git`、`node_modules`）。
  扫隐藏目录必须用 `os.walk`。**备份文件里同样会留隐私**，不能只清源文件。
- 用正则扫路径时注意转义层级：JS 字符串字面量里的 Windows 路径可能有
  1~4 层反斜杠，写规则时得同时覆盖单层和多层两种写法，否则会漏。
  （下面这行是示意写法，不是真实目录，扫描器命中它属于误报。）
  `D:\\Users\\x` 和 `D:\\\\Users\\\\x` 都得覆盖到。
- 产物要拿去当训练参考的话，**不能出现任何第三方作品名/IP**。
  注释里描述效果就写效果本身（"块状波浪带"、"立体屋顶"），不写"某某风格"。

跑一遍仓库自带的扫描器最省事：

```bash
node install/privacy-scan.js
```

## 八、干活硬规矩

1. **先核实，再动手。** 需求清单逐条对着现状过一遍，明确区分"已经有了"和
   "真正缺的"，并把核对结论回告。不做重复劳动，也不把"看起来完成了"当完成。
2. **证据优先于断言。** 说"完成"之前跑一遍验证，给可核对的数字。
   没把握的地方标"待确认"，不要含糊过去。
3. **删除一律走隔离区。** 用 `Move-Item` 移到临时隔离目录，不真删。
   合并重复目录前必须做 SHA256 逐字节比对 + 扫引用，不能只比大小。
4. **改了什么要说。** 自己拿主意改了什么、为什么改，交付时主动交代，
   并给"不合适你说"的口子。
5. **本机沙箱限制见技能** `workbuddy-sandbox-constraints`
   （被禁的 API、stdout 不回传、绝对路径要求）。
